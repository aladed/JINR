Исходя из предоставленных данных, архитектура суперкомпьютера «Говорун» представляет собой классическую гетерогенную среду с четким разделением на вычислительный (Bare-Metal) и сервисный (Virtualization) сегменты.
1. Сетевая топология (Скелет графа)
Архитектура сети построена не в виде 3D-Тора, а по двухуровневой топологии Spine-Leaf (Утолщенное дерево / Fat-Tree).
Верхний уровень (Spine / Корневые коммутаторы): Обеспечивают связь между нижними коммутаторами. Работают в режиме Failover (Отказоустойчивость): если один падает, трафик прозрачно перетекает на соседние.
Нижний уровень (Leaf / Листовые коммутаторы): К ним напрямую подключены серверы и массивы хранения данных (СХД).
Интерконнект: Используются две технологии — InfiniBand (100 Гбит/с) и Intel Omni-Path (OPA). Ethernet используется в основном для управляющей сети и новых GPU-узлов.
Охлаждение: Комбинированное жидкостное и воздушное («водяная/воздушная голова»).
2. Аппаратные узлы (Вершины графа: Hardware)
Вычислительные ресурсы сильно различаются. В графе это будут узлы разных типов с разными векторами признаков (фичами).
Тип 1: Базовые вычислительные узлы (Intel Cascade Lake / H04)
CPU: Intel Xeon Cascade Lake.
RAM: 192 ГБ DDR4.
Особенность (PMEM): Установлено по 4 модуля Intel Optane Persistent Memory (по 250 ГБ). Могут работать как сверхбыстрый диск или как расширение оперативной памяти. При обесточивании хранят данные 55–56 дней.
Тип 2: Вычислительные узлы / Хранилища (Intel Gold)
CPU: Intel Xeon Gold.
RAM: 512 ГБ.
СХД: 4 диска по 2 ТБ.
Сеть: InfiniBand 100 Gbps (по 2 сетевые карты на узел).
Тип 3: Тяжелые GPU-узлы (AMD EPYC + NVIDIA A100)
Количество: 5 серверов.
CPU: 2x AMD EPYC («эдик»), 64 ядра (суммарно 128 ядер на узел).
RAM: от 256 ГБ до 2 ТБ.
GPU: 8x NVIDIA A100 в каждом сервере.
Сеть: Ethernet 100 Гбит/с.
Тип 4: Сверхтяжелые GPU-узлы (NVIDIA H100 Hopper)
Количество: 2 сервера.
GPU: 8x NVIDIA H100 («хотера / AH сотых»), 80 ГБ видеопамяти каждая. Карты спарены (NVLink).
3. Логическая топология (Вершины графа: Software)
Здесь кроется самый важный инсайт для вашей GNN: кластер разделен на две принципиально разные зоны управления.
Зона научных расчетов (Bare-Metal): * На основных вычислительных серверах «Говоруна» нет гипервизоров и виртуальных машин.
Причина: Специфика сети Omni-Path, которая теряет производительность или не работает при пробросе в виртуалки.
Как моделировать в GNN: Ребра идут напрямую от Задачи (Job планировщика SLURM) к Физическому Хосту (Job -> hosted_on -> ComputeNode).
Зона обслуживания платформы (Service VMs):
Развернута на отдельных серверах. Здесь крутятся базы данных, управляющие узлы, системы мониторинга и т.д.
Гипервизоры: Используется XCP-ng 8.2/8.3 (open-source форк Citrix XenServer) и местами Proxmox.
Как моделировать в GNN: Классическая цепочка (Service -> hosted_on -> VM -> hosted_on -> ManagementNode).
Чтобы вам было проще визуализировать, как эти данные превращаются в граф для обучения нейросети, я подготовил интерактивный виджет топологии. Вы можете посмотреть, как устроен Spine-Leaf и как логически ложатся задачи.
Для обучения вашей GNN вам нужно создавать «слепки» (snapshots) этого графа в разные моменты времени. Вот 3 отличных сценария синтетических сбоев на основе интервью:
Каскад сети (Отказ Spine-коммутатора):
Сценарий: Один из Spine-коммутаторов начинает терять пакеты (hardware error).
Метрики: Рост packet_drop на коммутаторе -> Рост I/O wait на узлах с Intel Gold (не могут достучаться до СХД) -> Стагнация SLURM-задач на узлах Cascade Lake.
Задача GNN: Найти сломанный коммутатор, а не обвинять зависшие серверы.
Аномалия Persistent Memory (PMEM):
Сценарий: Узел H04 (Cascade Lake) перевел PMEM из режима RAM в режим диска из-за ошибки контроллера, либо память перегрелась.
Метрики: Резкое падение доступной RAM на хосте -> Задача падает с ошибкой OOM (Out of Memory).
Задача GNN: Связать падение конкретной задачи с аппаратной метрикой PMEM на физическом хосте.
Перегрев стойки GPU (Тепловой мешок):
Сценарий: Отказ контура жидкостного охлаждения на узлах с NVIDIA H100 (которые выделяют колоссальное количество тепла).
Метрики: Температура GPU растет -> Карты включают троттлинг (снижают частоты) -> Время выполнения задачи (Job) растягивается в 3 раза.
Задача GNN: Показать, что медленная работа программы вызвана аппаратным троттлингом из-за системы охлаждения.

Критическое топологическое правило: узлы GPU не должны оставаться изолированными. 1. Математический аппарат признаков
Для каждого из описанных нами ранее 100+ признаков (CPU, GPU, RAM, HDD, Switch, Job) вместо одного сырого числа $x_t$ мы будем рассчитывать вектор из 3 компонентов:
Текущее значение ($x_t$): Базовый срез телеметрии.
Мгновенная дельта ($\Delta_{short}$): Резкий импульс за шаг дискретизации ($\tau = 5$ секунд).
$$\Delta_{short} = x_t - x_{t-\tau}$$
Экспоненциальное скользящее среднее (EMA / $\Delta_{long}$): Показывает плавное накопление проблемы за окно $N$ тактов (например, 5 минут = 60 тактов) без необходимости хранить в памяти огромную историю сырых точек.
$$\mu_t = \alpha \cdot x_t + (1 - \alpha) \cdot \mu_{t-\tau}$$
Где коэффициент сглаживания $\alpha = \frac{2}{N + 1}$. Тренд вычисляется как разница текущего значения и сглаженного фона: $\Delta_{long} = x_t - \mu_t$.
2. Алгоритмическая реализация: Потоковый буфер (Ring Buffer)
Чтобы система работала эффективно на реальном суперкомпьютере, мы не можем сохранять всю историю в реляционную БД. Мы реализуем легковесный кольцевой буфер (Ring Buffer) прямо в оперативной памяти процесса сбора.
Вот как выглядит архитектурная логика вычисления на языке Python (для последующего переноса в Go-агенты или Polars-пайплайн):
Python
import numpy as np

class TelemetryProcessor:
def __init__(self, window_size_long: int = 60):  # 60 тактов * 5с = 5 минут
self.history = {}  # Хранилище последних состояний узлов
self.alpha = 2.0 / (window_size_long + 1)  # Коэффициент для EMA

def process_metric(self, node_id: str, metric_name: str, current_value: float):
key = f"{node_id}_{metric_name}"

if key not in self.history:
# Инициализация для нового узла/метрики
self.history[key] = {
"prev_value": current_value,
"ema": current_value
}
return current_value, 0.0, 0.0

hist = self.history[key]

# 1. Вычисление мгновенной дельты (Microburst)
delta_short = current_value - hist["prev_value"]

# 2. Вычисление скользящего тренда (EMA для детекции утечек)
hist["ema"] = (self.alpha * current_value) + ((1 - self.alpha) * hist["ema"])
delta_long = current_value - hist["ema"]

# Обновляем историю для следующего шага
hist["prev_value"] = current_value

return current_value, delta_short, delta_long

Правило формирования финальных матриц (Tensor Shape & Concatenation):
Для каждого типа узла сформируй финальную матрицу признаков x путем статической конкатенации.
1. Отдели непрерывные признаки (Continuous) от категориальных (Categorical).
